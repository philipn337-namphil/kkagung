# Phase 1 환경·인증·업로드 정책

상태: 보안·운영의 문서 작성 완료. 앱 구현·실행·배포 검증은 미완료.
기존 `../../docs/SECURITY_OPERATIONS.md` 및 `security-test-checklist.md`와 함께 적용한다.
이 문서의 추가 기준은 백엔드·인프라에 전달할 구현 계약이며 환경 변수만 추가해도 기능이 적용되는 것은 아니다.

## 환경 변수와 비밀 값

- 루트 `.env.example`은 인프라 담당이 최종 실행 가이드·Docker 설정과 통합한다. 중복 템플릿을 따로 유지하지 않는다.
- 공통으로 맞출 것은 변수 이름과 비밀이 아닌 설정이다. JWT 서명 키·개인 자격 증명을 팀원끼리 같은 값으로 맞출 필요는 없다.
- 로컬에서는 `.env.example`을 `.env`로 복사해 개인별 개발 값을 넣는다. 실제 운영 키나 실제 사용자 사진을 개발·시드에 사용하지 않는다.
- JWT 키는 암호학적 난수로 최소 32바이트를 생성하고 Base64 문자열로 환경 변수에 넣는다. 백엔드는 Base64 디코딩 후 키 길이를 확인한다.
- 운영 비밀은 서버에서 주입한다. 프론트 공개 환경 변수·Git·Docker 이미지·빌드 산출물에 DB 비밀번호, JWT 키, 저장소 키, AI API 키를 넣지 않는다.
- 앱 DB 계정은 실행에 필요한 권한만 갖는다. 마이그레이션용 DDL 권한은 별도 계정·실행 단계로 분리한다.
- `.env.example`의 포트·DB명·버킷명은 초안이다. 실제 코드가 로드하는 이름과 README 실행 절차를 인프라 담당이 최종 일치시킨다.
- 로컬 DB TLS 지원 여부는 실행 구성에 맞춰 명시한다. 운영 DB 통신은 TLS와 서버 인증서 검증을 사용한다.
- 키 노출 시 폐기·교체하고 기존 토큰을 무효화한다. 삭제 커밋만으로 해결하지 않는다.

## JWT·사용자 권한 계약

- Phase 1 Access Token은 JWT, HS256, 유효기간 900초로 한다. 서버 설정의 알고리즘만 허용하고 `none` 또는 요청이 선택한 알고리즘을 허용하지 않는다.
- 필수 클레임: `sub`(변하지 않는 사용자 ID), `iss`, `aud`, `iat`, `exp`, `jti`.
- 서버는 서명·발급자·대상·만료를 검증한다. 토큰에 생년월일·이메일·사진 경로 등 개인정보를 넣지 않는다.
- JWT 역할 클레임을 권한의 최종 근거로 쓰지 않는다. 현재 DB 계정의 역할·상태·성인 인증 여부를 검사한다.
- 인증 실패는 401, 인증된 사용자의 역할·상태·성인 인증 제한은 403으로 구분한다.
- 로그아웃은 해당 `jti`를 만료까지 폐기 목록으로 관리한다. 다중 서버에서 공유하는 저장소가 필요하다. 권한 회수·정지·탈퇴는 다음 요청부터 차단한다.
- Phase 1에서는 인증 Refresh Token을 추가하지 않는다. Access Token 만료 시 다시 로그인한다. 추천 새로고침권과 구분한다.
- 프론트는 Bearer 토큰을 메모리에 보관한다. URL·로그에 넣지 않는다. 새로고침 후 재로그인이 필요한 기본 동작으로 시작한다.
- 가입·인증 완료·로그인 등 공개 허용 엔드포인트를 명시하고 나머지는 기본 인증 필요로 한다. 인증 진행 중 계정은 인증 관련 동작만 허용한다.
- 성인 인증은 서버가 제공자 결과를 검증한다. 개발용 인증 대체 수단은 운영에서 활성화할 수 없게 한다.
- 비밀번호는 검증된 라이브러리의 적응형 단방향 해시로 저장한다. 평문 저장·복호화 가능한 암호화를 사용하지 않는다.
- 관리자 API의 세부 규칙은 `../../docs/SECURITY_OPERATIONS.md` 2절을 적용한다. 로컬에서는 루프백 주소만 허용하고, 운영 전용 도메인·IP 제한은 인프라 배포 단계에서 검증한다.

## 사진 업로드 계약

- 파일당 최대 10 MiB, 디코딩 후 최대 2천만 픽셀, 사용자별 원본은 최대 3장으로 시작한다. 동시 업로드도 개수 제한을 우회하지 못하게 한다.
- 허용 형식은 JPEG·PNG·WebP로 제한한다. 확장자·요청 Content-Type뿐 아니라 실제 디코딩 결과를 확인한다. SVG·실행 파일 등은 거부한다.
- 서버가 객체 키와 저장 위치를 정하고, 업로드 사용자의 소유권을 검증한다. 사용자 입력 경로를 사용하지 않는다.
- 원본은 로컬에서도 웹 정적 제공 디렉터리 밖의 `storage/private/originals/`에 저장한다. 이 디렉터리는 Git 무시 대상이다.
- 운영에서는 비공개 원본 버킷을 사용한다. AI·흐림 최종 파일은 별도 공개용 버킷과 경로에 둔다. 구체적 기준은 기존 운영 문서 3절을 따른다.
- 이미지 처리 시 방향을 반영한 뒤 EXIF 등 메타데이터를 제거하고 검증된 이미지로 재인코딩한다. 변환 실패 시 원본 공개로 대체하지 않는다.
- 업로드·변환 요청에 속도 제한과 AI 호출 한도를 둔다. 외부 AI 전송에는 필요한 사진 데이터만 전달하고 제공자의 데이터 처리 조건을 운영 전에 확인한다.
- 오류 응답에 스토리지 자격 증명·내부 파일 경로·원본 객체 키를 노출하지 않는다.

## Phase 1 운영 점검 및 인수인계

보안·운영 담당은 정책·무시 규칙·체크리스트를 전달하고, 백엔드는 인증·업로드 검사와 설정 로딩을 구현한다. 인프라는 README·로컬 DB·Docker 등 실행 환경을 제공한다.

| 점검 | 완료 근거 | 현재 상태 |
|---|---|---|
| 비밀값 미커밋·원본 비공개 기준 | 이 문서 및 기존 운영 문서 | 작성 완료 |
| 환경 변수 예시·Git 무시 규칙 | 루트 두 파일 | 작성 완료, 로컬 임시 Git에서 11개 무시 규칙 사례 통과 |
| JWT·관리자·업로드 검사 | API 통합 테스트 | 백엔드 구현 후 검증 |
| 신규 DB 마이그레이션·시드 | 빈 DB에서 실행한 기록 | 백엔드·인프라 확인 필요 |
| 팀 전원 동일 실행 | 동일 develop 커밋·각자 실행 확인 | 미확인 |

팀 전원 확인 절차:

1. 저장소 담당자가 변경을 통합한 develop 커밋 SHA를 기록한다.
2. 각 팀원은 같은 SHA에서 README만 따라 개인 `.env`를 준비한다.
3. 지정된 절차로 개발용 빈 DB를 준비하고 마이그레이션·시드를 실행한다. 기존 데이터가 있는 DB를 임의로 지우지 않는다.
4. 서버·프론트 실행, 로그인·프로필·선호 조건·홈 화면을 확인한다. 목업인 화면은 명시한다.
5. 일반 사용자 관리자 API 차단, 원본 정적 접근 차단을 확인한다.
6. 담당자별 OS·런타임/Docker 버전·커밋 SHA·결과·막힌 점을 남긴다. 전원 확인 전에는 Phase 1 전체 완료로 보고하지 않는다.

|---|---|---|---|---|---|
| 프론트엔드 | 미확인 | 미확인 | 미확인 | 미확인 | - |
| 백엔드·DB | 미확인 | 미확인 | 미확인 | 미확인 | - |
| 인프라 | 미확인 | 미확인 | 미확인 | 미확인 | - |
