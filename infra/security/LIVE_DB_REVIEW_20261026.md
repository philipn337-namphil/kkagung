- 기존 통합 대기 6개 중 차단·감사 로그 2개를 실제 실행으로 전환했다. **대기 4개**: 원본 사진, 업로드 검증, 전체 권한·계정 상태 조합, 사진/NAS를 포함한 운영 복구.

최종 증빙: `evidence/portable-db-drill.json`, `evidence/live-db-audit.json`. 실행 도구의 식별자·포트·loopback·정리 소유권 경계 시험도 4/4 통과했다. 이 도구 시험은 DB 보안 검증 수에 포함하지 않는다.

첫 PR #19 실행은 94 통과·2 실패·17 미실행이었고, 새 백엔드 브랜치 실행은 112 통과·2 실패였다. 공개 이미지 테스트가 endpoint만 설정하고 공개 bucket은 환경에 기대고 있어 가상 bucket 이름을 도구에서 명시한 후 최종 114/114로 통과했다. 초기 기동 훅에는 60초, 개별 테스트에는 30초를 허용했다. 앱·테스트의 기대 결과는 수정하지 않았다. 이전 결과도 `portable-db-claims-pr19.json`, `portable-db-before-public-config.json`에 보존했다.

## 실행 환경

2026-10-26(KST), 사용자 요청에 따라 운영 자원 없이 로컬 격리 환경을 준비했다. 공식 MySQL 8.4.13 Windows ZIP을 내려받아 공식 페이지의 MD5 `7b94489d5524dea9b27097068bea25a8`과 일치함을 확인했다. 배포 출처: https://dev.mysql.com/downloads/mysql/8.4.html?os=3 . MD5는 배포 파일 일치 확인이며 강한 서명 검증으로 표현하지 않는다.

한글 도구 경로에서 MySQL 기동이 실패하여 영문 TEMP 경로에 도구를 배치했다. Windows 서비스·시스템 PATH·방화벽 규칙은 변경하지 않았다. 매 실행 새 데이터 디렉터리·임의 포트·임의 비밀번호를 만들며, TCP는 127.0.0.1에만 바인딩하고 MySQL X 포트는 비활성화한다. 기존 DATABASE_URL은 사용하지 않는다. 시드는 가상 계정뿐이다.

## 재실행

```powershell
# 공식 ZIP의 체크섬을 검증하고 영문 경로에 압축을 푼 뒤 실행한다.
node infra/security/portable-db-drill.mjs 'C:/Users/82102/AppData/Local/Temp/kkagung-mysql-8.4.13-tools' '../kkagung-security-claims/backend'
node --test infra/security/tests/isolated-db-drill.test.mjs

# Docker가 있는 팀원을 위한 대안. --plan은 DB를 건드리지 않는다.
node infra/security/isolated-db-drill.mjs --plan
node infra/security/isolated-db-drill.mjs --run
```

portable 실행의 두 번째 인자는 검증할 백엔드 폴더다. 대상 코드는 해당 폴더의 HEAD로 증빙에 기록한다. 앱·Prisma 의존성이 설치되어 있어야 한다. 개발 토큰 문제가 남은 develop에서는 관련 테스트가 실패할 수 있으므로 결과의 대상 커밋을 반드시 확인한다. Docker 대안의 실제 컨테이너 경로는 이 PC에서 실행 검증하지 못했다.

증빙은 `evidence/portable-db-drill.json`이다. 단계별 성공 여부와 테스트 이름·판정만 기록하고 자식 프로세스의 원문 오류·토큰·비밀번호·덤프는 공개하지 않는다. 덤프는 메모리에서만 복원한다. 임시 초기화 SQL은 기동 후 또는 실패 시 지우고, 종료 시 자신이 시작한 서버를 중지한다. 진단용 가상 데이터 디렉터리는 Git 밖에 남는다. 재실행은 기존 디렉터리를 재사용하지 않는다.

## 대기 6개 판정 기준

| 항목 | 실제로 완료해야 할 시험 | 담당 / 범위 |
|---|---|---|
| 원본 사진 | 수락 전·제3자 거부, 수락 후 참여자 허용, 서명 URL 만료 및 익명 버킷 접근 거부 | 백엔드·인프라 구현 후 보안 검증. 현재 originalImages는 항상 빈 배열이므로 성공 경로 검증 불가 |
| 차단 관계 — 완료 | 양방향 신규 요청·수락·메시지 거부 및 실제 DB 쓰기 없음 | 실제 HTTP+DB 전용 시험 통과. 경쟁 상태에서 동시 차단하는 모든 경우까지 보장한다는 뜻은 아님 |
| 감사 로그 — 완료 | 설정 변경 전후 값·관리자·실제 저장, 잘못된 입력 시 변경 없음 | 새 Prisma 연결에서 DB 감사 행 조회 통과. 프로세스 강제 종료·DB 장애 주입 시험은 아님 |
| 업로드 | 실제 바이너리 확장자 위조·MIME·용량·픽셀·EXIF 검사 | 백엔드 업로드 구현 필요. 현재 이미지 상태는 501, 업로드 검증 경로 부재 |
| 권한·계정 상태 | 추천·하트·채팅 소유권 및 정지·탈퇴·차단 전이 | 백엔드·보안. 기존 테스트 통과만으로 모든 상태 조합이 완료됐다고 판정하지 않음 |
| 복구 | DB 복원 건수·해시·관계, 사진·NAS 복원과 접근 권한, 운영 목표 RPO/RTO 측정 | 로컬 DB 덤프 복원은 일부 검증. 클라우드·사진·NAS·운영 복구 목표는 별도 |

기존 `it.skip` 6개는 위 요구 묶음의 자리표시자였다. 차단·감사 항목은 실제 DB 실행 파일로 옮겨 나머지 4개만 skip으로 유지했다. 로컬 도구 안전성 시험을 통과해도 DB 통합 항목의 성공으로 옮기지 않는다. 실제 수행한 테스트와 남은 하위 조건을 구분해 기록한다.

## 추가 백엔드 브랜치 확인

`feature/backend-admin-concurrency` debe139에는 종결 신고의 재처리 409와 제재 동시성 시험 계약 수정이 추가됐다. 서로 다른 제재가 순서대로 적용되는 경우는 허용하고 감사 로그 before/after 연속성과 최종 상태 일치를 검사한다. 소스상 앞선 계약 불명확성은 정리됐지만, 병합 상태와 실제 DB 실행 결과는 별개다. 테스트 setup의 `rateLimitCounter.deleteMany({})` 전체 삭제는 여전히 존재하므로 공유 DB에서 직접 테스트를 실행하면 안 된다. 이번 실행 도구가 생성한 전용 DB에서만 수행한다.
