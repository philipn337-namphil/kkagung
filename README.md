# 까궁 (kkagung)

매일 오전 8시에 새로 열리는 운세와 익명 AI 프로필 카드로 호감을 표현하는 성인 대상 매칭 서비스입니다.

> 운세는 오락 목적이며, 실제 사진과 상세 프로필은 **상대가 채팅 요청을 수락한 뒤에만** 서로 공개합니다.

## 오늘 구현 범위 (MVP)

- 회원가입·로그인, 프로필·선호 조건 등록
- 오전 8시 기준 오늘의 운세와 추천 카드 3·5·7장 조회
- 하트, 채팅 요청, 수락 후 채팅방 생성 및 실제 프로필 공개
- 선착순 새로고침권 발급 및 카드 새로고침
- 관리자: 사용자·신고 관리, 인기 배지 기준·선착순 인원 설정

## 브랜치 구조

| 브랜치 | 용도 | 직접 작업자 |
|---|---|---|
| `main` | 실행 가능한 안정 버전. 직접 커밋 금지 | 팀장 병합만 |
| `develop` | 기능 통합·테스트 브랜치 | 모든 팀원은 PR로 병합 |
| `feature/frontend` | 사용자 화면 및 관리자 화면 UI | 이재원 |
| `feature/backend-db` | API, DB 설계·마이그레이션, 추천·관리자 로직 | 백엔드·DB 담당 |
| `feature/infra` | Docker, 배포 스크립트, NCP 인프라 문서·구성 | 남필량 |
| `feature/security-ops` | 보안 설정, 접근 제어, 로그·백업·운영 점검 | 김서현 |

### 반드시 지킬 규칙

1. `main`에 직접 push하지 않는다. 각 역할 브랜치에서 작업하고 `develop`으로 PR을 만든다.
2. 다른 역할의 파일을 바꿔야 하면 담당자에게 먼저 알리고, 불가피한 변경은 PR 설명에 명시한다.
3. 비밀번호, API 키, JWT 시크릿, 실제 사용자 사진, `.env`, DB 덤프는 절대 커밋하지 않는다.
4. API를 추가·변경하면 `docs/03_API_명세서.md`도 같은 PR에서 수정한다.
5. DB 스키마를 변경하면 마이그레이션 파일과 `docs/04_ERD_및_테이블정의.md`를 함께 수정한다.
6. 실제 원본 사진은 서버에서만 접근 가능한 비공개 저장소에 두며, 채팅 수락 전에는 브라우저에 원본 URL을 전달하지 않는다.

## 역할별 시작 안내 — 에이전트용

아래 역할을 맡은 에이전트는 **자신의 브랜치만 기준으로 작업**합니다. 기술 스택이나 API 형식이 확정되지 않은 부분은 임의로 대규모 변경하지 말고, 최소 실행 가능한 형태로 제안하거나 팀장에게 질문합니다.

> **작업 시작 전 [docs/06_결정사항_및_작업배분.md](docs/06_결정사항_및_작업배분.md)를 먼저 읽으세요.** 팀에서 확정한 결정사항, 역할별 작업 목록, 수정 허용 파일 범위, 아직 정해지지 않아 질문해야 할 항목이 정리돼 있습니다.

### 프론트엔드 — `feature/frontend`

- 담당 폴더: `frontend/`
- 구현: 로그인·가입, 프로필·선호 조건, 오늘의 운세/추천 카드, 하트·메시지함·채팅, 마이페이지, 관리자 UI
- 관리자 UI 범위: 대시보드, 사용자·신고 목록, 배지 기준, 선착순 인원 설정
- API 계약은 `docs/03_API_명세서.md`를 우선 기준으로 사용한다. API가 아직 없으면 목업 데이터를 분리해 화면을 먼저 만든다.
- `backend/`와 DB 마이그레이션은 변경하지 않는다.

### 백엔드·DB — `feature/backend-db`

- 담당 폴더: `backend/`, `docs/03_API_명세서.md`, `docs/04_ERD_및_테이블정의.md`
- 구현: 인증·권한, 프로필/선호 조건, 오늘의 운세, 카드 추천, 하트·채팅 요청·채팅방, 관리자 API
- 핵심 데이터 규칙: 오늘의 카드 중복 추천 금지, 하루 1회 새로고침권 발급, 선착순 재고는 원자적으로 차감, 수락 전 원본 사진 비공개, 차단·신고 사용자 제외
- DB 변경은 마이그레이션으로만 적용한다. 시드 데이터에는 가상 사용자만 넣는다.
- 프론트가 바로 연결할 수 있도록 요청/응답 예시와 오류 형식을 `docs/03_API_명세서.md`에 유지한다.

### 인프라 — `feature/infra`

- 담당 폴더: `infra/`, 배포 관련 루트 설정 파일
- 구현: 로컬 실행 환경, Docker/배포 설정, 환경변수 예시, NCP 구성 문서
- NCP 방향: VPC·Public/Private Subnet·ACG/NACL로 웹/관리자/DB 분리, Load Balancer·Auto Scaling·Cloud Insight로 오전 8시 집중 대응, Cloud DB for MySQL HA/백업, Object Storage 원본·공개 이미지 분리
- 애플리케이션 소스의 기능 로직은 변경하지 않는다. 필요한 환경변수는 `.env.example`에 키 이름만 추가한다.

### 보안·운영 — `feature/security-ops`

- 담당 폴더: `infra/security/`, `docs/SECURITY_OPERATIONS.md` 및 운영 설정
- 구현: 관리자 역할 접근 제어 점검, API 입력 검증·속도 제한 정책 제안, 업로드 파일 정책, 로그·모니터링·백업·복구 점검표
- 확인 항목: 비밀값 미커밋, CORS/인증 정책, 원본 사진 접근 차단, 관리자 설정 변경 감사 로그, 신고·차단 흐름, DB 백업 복구 절차
- 기능 API의 비즈니스 로직은 백엔드 담당과 합의 후 변경한다.

## 작업 시작 방법

```bash
git clone https://github.com/philipn337-namphil/kkagung.git
cd kkagung
git fetch origin
git switch feature/<내-역할-브랜치>
git pull origin feature/<내-역할-브랜치>
```

작업을 마치면 다음 순서로 올립니다.

```bash
git add <변경한-파일>
git commit -m "feat: 무엇을 구현했는지"
git push origin feature/<내-역할-브랜치>
```

GitHub에서 `feature/...` → `develop` Pull Request를 만들고, PR 본문에 **변경 내용 / 실행 방법 / 확인한 결과 / 다른 역할에 필요한 변경점**을 적습니다.

## 폴더 구조

```text
kkagung/
├─ frontend/                 # 사용자·관리자 웹 화면
├─ backend/                  # API 서버, DB 마이그레이션·시드
├─ infra/                    # Docker, 배포·NCP 구성
│  └─ security/              # 보안·운영 정책과 점검 자료
├─ docs/                     # API, ERD, 운영 문서
├─ .env.example              # 키 이름만 담은 환경변수 예시
└─ README.md
```

## 공통 환경변수

`.env.example`을 복사하여 각자 `.env`를 만든다. `.env`는 공유하거나 커밋하지 않는다.

```bash
cp .env.example .env
```
